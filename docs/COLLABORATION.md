# Codex × Claude 协作约定

> 生效：2026-09-05。适用于本仓库上 Codex 与 Claude 的所有协作。
> 本文件是**约定本身**；具体某轮工作的内容不写在这里，写在按 §2 命名的文档里。

## 0. 唯一信道

**`docs/` + git 是唯一协作信道。** 不读对方的 session 状态、不看对方的进程、不进对方的工作树窥探进度。

理由：session 状态是**过程**，不是**承诺**——读到的可能是半句话、下一秒就被推翻的中间结论。而提交进 git 的文档是签过字的：作者知道它会被对方当依据，写的时候就得为它负责。协作要建立在后者上。

推论（都从上面这条来）：

- **要知道对方干到哪了 → 读 `git log` 与该轮文档**，不去翻 session。
- **要交东西给对方 → 提交进 git**，不在对话里口头交待。没提交 = 没交付。
- **对方没写进文档的，就是没做**。不替对方脑补进度，也不追认「它应该已经做了」。
- 两边不同时改同一批文件。交接靠分支与文档，不靠时序默契。

## 1. 一轮协作的形状

```
用户提出目标
   ↓
[工单]  WORK_ORDER      —— 谁做、做什么、验收标准、边界（不许做什么）
   ↓
[执行]  EXECUTION_LOG   —— 执行方逐批记录：改了什么、证据、跳过与原因
        EXPERIMENT_*    —— 有实验则另立，含负结果
   ↓
[审查]  REVIEW          —— 另一方独立审查，只出结论不改代码
   ↓
[修复]  FIXES           —— 被审方（或审查方）按 review 修，逐条回执
   ↓
[交接]  HANDOFF         —— 复现命令、边界、未尽事项
   ↓
用户确认 → 合并 → [部署] DEPLOYMENT —— 实际做了什么的回执
   ↓
未尽事项 → OPEN_ITEMS.md（见 §4）
```

不是每轮都要走满七步。小改动直接提交 + 在 commit message 里说清即可；**只有跨会话、跨 agent、需要对方接手的工作才立文档**。判断标准：*对方不读这份文档就接不上手* → 立；否则不立。

## 2. 文档命名与导航

2026-09-05 按用户要求统一治理，完整规范与旧名映射见 [GOVERNANCE.md](GOVERNANCE.md)，文件身份登记在 [catalog.json](catalog.json)。

```text
docs/<guides|plans|research|records>/<topic>_<producer>_<YYYYMMDD>.<md|html>
```

- 作者标记指原始执笔者（codex／claude／cursor 等），审查人和代提交人另记；无法确认就 unknown。模型版本仅在有依据时写正文。
- 日期优先保留原文档身份，缺日期时按治理规范追溯；修订只更新正文日期，不因换维护工具重新命名。
- 本次集中改名同步仓库内引用并留旧名映射；固定 SHA 历史链接和冻结脚本保持原样。
- README、COLLABORATION、OPEN_ITEMS、GOVERNANCE 及 catalog 保留固定入口。
- 新文档必须登记 catalog 并加入 docs/README 的对应类别；关键工单／规范同步根 README，其余由全量索引承接。提交前运行 `python3 scripts/check_docs.py`。

## 3. 每份文档的头三行

不论哪个阶段，开头必须交代清楚这四件事——**接手的人先看这里就能判断能不能信、能不能用**：

| 项 | 为什么必须有 |
| --- | --- |
| **基线 SHA** | 「在哪个提交上做的」。没有它，读者无法判断结论是否已过期 |
| **分支 / 工作树路径** | 「东西在哪」。跨 agent 时对方要能找到 |
| **状态** | 已完成 / 进行中 / 仅结论未改代码 / 已合并 |
| **边界** | **做了什么、明确没做什么**。见 §5 |

现有文档已是这个样子，照抄格式即可（例：[执行日志](records/ml-upgrade-execution-log_codex_20260904.md)、[审查报告](records/ml-upgrade-review_claude_20260904.md)）。

## 4. 未尽事项去 `OPEN_ITEMS.md`

**一轮的收尾文档不是未尽事项的归宿。** 修复回执写完就沉底了，挂在里面的待办没人会再翻出来。

所以：任何一轮结束时仍未做完的事，**必须登记到 [`docs/OPEN_ITEMS.md`](OPEN_ITEMS.md)**，并保留原始编号（如 `P2-3`）与出处链接。那份清单是跨轮次的唯一待办来源；开新一轮工单时先读它。

关掉一项时在清单里标记完成并写明由哪个提交/文档关闭，**不要直接删行**——删掉就看不出它曾被判断过。

## 5. 边界写「没做什么」，不只写「做了什么」

这是本仓库协作里最容易出事的地方，单独列出来。

执行方必须显式声明**没有做**的高风险动作，逐条列，不用「其余未做」一笔带过。本仓库涉及真实持仓与真实资金，以下每项都要明确表态：

- 是否合并 main / 推送远端
- 是否碰过原运行目录的数据库（`data/mystock.db`、`data/ml/mystock_ml.db`）
- 是否重启过 8888 服务
- 是否发布过公网报告（`ml.sh publish`）
- 是否新增过 cron / launchd 等自动调度
- 是否有任何真实下单或交易操作

原因很直接：这些动作**不可逆或对外可见**。审查方要能一眼确认「它没动生产」，而不是从几千行 diff 里自己推断。声明为假比不声明更糟——所以只写确实核实过的。

## 6. 数据隔离

- 实验、训练、迁移演练一律在**自己的工作树 + 数据副本**里做，不写原运行目录。
- `data/`、`*.db*`、`config.yaml` 已在 `.gitignore`，**绝不提交**（仓库公开）。
- 文档里可以写口径、比例、结论，**不写真实持仓金额与账户明细**。需要举例时用合成值并标注「合成测试值」。
- 交接文档给复现命令，不给数据本身；哈希与 manifest 留在本地 ignored 目录，文档只说去哪找。

## 7. 结论照实写

沿用项目既有纪律（见 [`ml-tier1-robustness_claude_20260718.md`](records/ml-tier1-robustness_claude_20260718.md)）：

- **负结果照写。** 打不过基线就写打不过，不调低门槛、不挑窗口。
- **工程完成 ≠ 模型晋级。** 两件事分开表述，不用前者的完成度暗示后者。
- **重建 / 回填 ≠ live。** 事后重算的预测必须标注来源，不能冒充当时真的给出过。
- 不确定就写不确定，别用含糊措辞把不确定磨平。

对方写了不实结论时，审查照实指出——这是审查这一步存在的意义。

## 8. 提交信息

commit message 是最轻量的协作信道，跨 agent 时经常是对方最先读到的东西：

- 说清**为什么**，不只是改了什么。
- 关联文档写路径，关联发现写编号（`P2-3`）。
- 协作产出的提交带 `Co-Authored-By`。
- 一轮里分批提交，别攒成一个巨型提交——审查方要能按批次读 diff。
